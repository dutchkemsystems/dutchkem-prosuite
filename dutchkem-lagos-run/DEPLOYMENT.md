## 3. Local Development

### 3.1 Backend

```bash
cd dutchkem-lagos-run/backend
cp .env.example .env
```

Fill the three signing secrets with freshly generated values:

```bash
openssl rand -hex 32   # SESSION_SIGNING_SECRET
openssl rand -hex 32   # SCORE_SIGNING_SECRET
openssl rand -hex 32   # RECEIPT_SIGNING_SECRET
```

Then:

```bash
npm install
npm run dev            # nodemon server.js  → http://localhost:4000
# or: npm start
```

Health check in a second terminal:

```bash
curl -s http://localhost:4000/health
# {"status":"ok","brand":"Dutchkem Ventures","service":"Lagos Run Backend", ...}
```

Useful local guards:

- Missing signing secrets only **warn** in development; in `NODE_ENV=production` the process refuses
  to start. That asymmetry is intentional — never ship a development start to production.
- `ALLOWED_ORIGINS` must include the client's dev origin (`http://localhost:5173`), exactly, with no
  wildcard and no trailing slash.
- Kora calls go to `KORAPAY_BASE_URL`. Point it at a mock (`http://127.0.0.1:4021`) when you do not
  want to touch the network; leave it unset to use `https://api.korapay.com/merchant/api/v1`.
- The webhook route needs the **raw** body; it is mounted above `express.json()`. If you reorder
  middleware, signature verification breaks.

### 3.2 Client

```bash
cd dutchkem-lagos-run
cp .env.example .env          # public values only
```

Fill `API_BASE_URL`, `ADMOB_REWARDED_ID`, `ADMOB_INTERSTITIAL_ID`, `APP_VERSION` (and optionally
`SENTRY_DSN`), then:

```bash
npm install                   # sharp, terser, javascript-obfuscator, dotenv, serve
npm run icons                 # renders client/icons/*.png from the danfo mark
node build.js --dev           # copies client/ → dist/, injects config.js, versions sw.js
npx serve dist                # http://localhost:3000
```

`npm run dev-client` serves the raw `client/` directory on port 5173 for quick edits, but it does
**not** inject `config.js` or version the service worker — use `build.js --dev` whenever you need to
test the real service-worker and config path. Unregister the old worker in DevTools → Application
when switching between the two.

### 4.1 Client — public, baked into `dist/config.js` by `build.js`

Everything here ships to the browser. Treat it as public.

|----------|----------|---------|
| `API_BASE_URL` | yes | API origin, e.g. `https://api.lagosrun.dutchkem.com` |
| `ADMOB_REWARDED_ID` | yes | Rewarded ad unit id (`ca-app-pub-…/…`) |

## 5. Kora Pay Setup

1. **Create the account** at Kora Pay with the Dutchkem Ventures business email.
2. **Verify the business** — CAC registration, director ID, settlement bank account. Checkout stays in
   test mode until verification completes. Do this first; it is the long pole.
3. **Get keys.** Dashboard → Settings → API Keys:
   - Test: `pk_test_…`, `sk_test_…`, plus the encryption key.
   - Live: `pk_live_…`, `sk_live_…`, plus the live encryption key.
   Put the **secret** and **encryption** keys only in the host's environment; the public key may ship
   to the client. Kora signs webhooks with the **secret key**, so no separate webhook secret is
   required — `KORAPAY_WEBHOOK_SECRET` is an optional override used only to accept a second key during
   a rotation window.
4. **Configure the webhook.** Dashboard → Settings → Webhooks → add:
   ```
   https://dutchkem-lagos-run-api.onrender.com/api/purchases/kora/webhook
   ```
   (or `https://api.lagosrun.dutchkem.com/api/purchases/kora/webhook` once the custom domain is
   attached — the host must match `KORA_WEBHOOK_URL` exactly). Subscribe to `charge.success`. The route
   verifies `x-korapay-signature` — an HMAC-SHA256 of `JSON.stringify(body.data)` keyed with the
   secret key — over the **raw** body, so do not put a body-rewriting proxy in front of it.
   Test and live modes keep separate webhook registrations: re-register after switching keys.
5. **Whitelist the redirect URL.**
   ```
   https://lagosrun.dutchkem.com/?kora_return=1
   ```
   The browser returns there after checkout; the client polls
   `GET /api/purchases/kora/status?reference=…` and kobo is granted only when the webhook has landed.
6. **Test-mode verification.**
   - `POST /api/purchases/kora/initialize` with a test session and `{ "sku": "kobo_500", "email": "…", "name": "…" }`
     → expect `checkout_url`.
   - Complete the test charge in Kora's checkout.
   - Confirm the webhook arrives (Kora dashboard → Webhooks → deliveries) and the response is
     `200 {"ok":true,"status":"ok"}`.
   - Confirm `/api/purchases/kora/status` reports `verified: true` and the wallet balance rose.
   - Replay the same delivery: expect `200 {"status":"already granted"}` and **no** second credit.
7. **Go live.** Swap to live keys, re-verify the webhook URL and redirect whitelist in live mode, run
   one real ₦100 charge, and refund it from the dashboard to prove the full loop.

Kora is the **web/PWA** rail only. Native builds use Play Billing / StoreKit (see §15).

## 6. Build the Client

```bash
cd dutchkem-lagos-run
npm ci
npm run icons
node build.js --dev      # sanity build
node build.js --prod     # release build: terser + javascript-obfuscator
```

What `build.js` does, in order:

1. Loads `.env` and **fails** if a required public variable is missing.
2. Clears and recreates `dist/`.
3. Copies the static shell (`index.html`, `styles.css`, `game.js`, `sw.js`, `manifest.json`, legal
   pages, `robots.txt`, `sitemap.xml`) and `icons/`.
4. Writes `dist/config.js` from the public env values plus `BUILD_TIME`.
5. Production only: minifies with terser, then obfuscates (control-flow flattening, string array with
   base64 encoding, self-defending, hex identifiers).
6. Rewrites `CACHE_VERSION` in `dist/sw.js` to `dutchkem-v<APP_VERSION>-<hash>` and **fails** if the
   line is not found, so a stale cache can never ship silently.
7. Runs the secret scan over `dist/` and exits non-zero on any hit.
8. Prints mode, version, file count, total size and build time.

Secret leak check (run it even though the build does — defence in depth, and it covers hand-patched
builds):

```bash
grep -rEil 'SIGNING_SECRET|KORAPAY_SECRET|PRIVATE_KEY|service_account|APPLE_SHARED_SECRET|GOOGLE_PLAY_SERVICE_ACCOUNT' dist/ \
  && echo "❌ SECRET LEAK — do not deploy" || echo "✅ clean"
```

Also confirm the API origin baked into the bundle is the production API, not localhost:

```bash
grep -o '"API_BASE_URL": *"[^"]*"' dist/config.js
```

## 7. Deploy the Backend

The backend is an Express 4 app that exports the app (`module.exports = app`) and only listens when
run directly, which is exactly what serverless wrappers expect.

### 7.1 Vercel (alternative — serverless; §7.2 is the recommended target)

`backend/vercel.json`:

```json
{
  "version": 2,
  "builds": [{ "src": "server.js", "use": "@vercel/node" }],
  "routes": [{ "src": "/(.*)", "dest": "server.js" }]
}
```

Deploy:

```bash
cd dutchkem-lagos-run/backend
vercel link                      # create/attach the project
vercel env add SESSION_SIGNING_SECRET production   # repeat per secret (§4.2)
vercel --prod
```

Then attach `api.lagosrun.dutchkem.com` in Project → Settings → Domains.

Caveats on serverless:

- **The file database does not survive** across invocations on Vercel. Move `DB_PATH` to Postgres
  (Supabase) before pointing real traffic at it; the file store is fine for staging and demos.
- **Cron/keep-alive:** the webhook must be reachable cold; there is no long-running process to warm.
- **Body parsing:** the Kora webhook route needs the raw body. Vercel's Node runtime preserves the
  request stream, so the existing `express.raw()` mount keeps working — do not enable a platform-level
  body parser in front of it.

### 7.2 Render (recommended — a real process and a persistent disk)

**Blueprint (fastest).** `dutchkem-lagos-run/render.yaml` is a **single-service** Blueprint for this
project only, so applying it cannot create, modify or delete any ProSuite resource: node runtime,
`rootDir: dutchkem-lagos-run/backend` (resolved from the repository root, not from the file's folder),
`NODE_ENV=production`, a 1 GB disk mounted at `/var/data` with `DB_PATH=/var/data/lagosrun.db`,
Render-generated session/score/receipt secrets, and the Kora variables prompted at apply time.

1. Dashboard → **New → Blueprint** → connect `dutchkemsystems/dutchkem-prosuite` → pick the branch.
2. Set **Blueprint Path** to `dutchkem-lagos-run/render.yaml`. Render defaults to `render.yaml` at the
   repository root — that file is ProSuite's and must not be applied here. (If you ever do point a
   Blueprint at the root file, it declares both services and would try to reconcile `dutchkem-api`.)
3. Review the plan before applying: it must show **one** new resource, `dutchkem-lagos-run-api`, and no
   changes to `dutchkem-api`. Cancel rather than apply if `dutchkem-api` appears.
4. When prompted, paste `ALLOWED_ORIGINS` (the exact Vercel origin and the production domain,
   comma-separated, no trailing slash, no wildcards) and the four `KORAPAY_*` live values from the
   Kora dashboard. Never commit them.
5. Note the assigned URL — `https://dutchkem-lagos-run-api.onrender.com` for the service name in
   `render.yaml`. That host is both the client's `API_BASE_URL` and the Kora webhook host. If the name
   was taken and Render appended a suffix, update `KORA_WEBHOOK_URL` and rebuild the client.
6. `starter` is not optional: a free instance has no disk, so wallet balances would reset on every
   deploy and a paid top-up would vanish.

**Manual dashboard path.**

1. New → Web Service → connect the repo → root directory `dutchkem-lagos-run/backend`.
2. Build `npm ci`, start `npm start`.
3. Add every variable from §4.2, `NODE_ENV=production`, `PORT` left to Render.
4. Add a **persistent disk** mounted at `/var/data` and set `DB_PATH=/var/data/lagosrun.db`.
5. Health check path `/health`; enable auto-deploy on the release branch only.
6. Add the custom domain `api.lagosrun.dutchkem.com`.

### 7.3 Firebase Cloud Run (alternative)

```bash
cd dutchkem-lagos-run/backend
```

## 8. Deploy the Client

`dist/` is a static site. Serve it from the domain root so the service worker's scope is `/`.

### 8.1 Vercel

`client/vercel.json` is copied into `dist/` by `build.js`, so the built folder deploys as a static
site with no build step on Vercel's side (no `.env`, no `npm install`, nothing to configure):

```json
{
  "version": 2,
  "rewrites": [{ "source": "/(.*)", "destination": "/index.html" }],
  "headers": [
    {
      "source": "/sw.js",
      "headers": [
        { "key": "Cache-Control", "value": "no-cache, no-store, must-revalidate" },
        { "key": "Service-Worker-Allowed", "value": "/" }
      ]
    },
    {
      "source": "/config.js",
      "headers": [{ "key": "Cache-Control", "value": "no-cache" }]
    },
    {
      "source": "/manifest.json",
      "headers": [{ "key": "Cache-Control", "value": "no-cache" }]
    },
    {
      "source": "/icons/(.*)",
      "headers": [{ "key": "Cache-Control", "value": "public, max-age=31536000, immutable" }]
    },
    {
      "source": "/(.*)",
      "headers": [
        { "key": "Strict-Transport-Security", "value": "max-age=31536000; includeSubDomains; preload" },
        { "key": "X-Content-Type-Options", "value": "nosniff" },
        { "key": "Referrer-Policy", "value": "strict-origin-when-cross-origin" },
        { "key": "Permissions-Policy", "value": "camera=(), microphone=(), geolocation=()" }
      ]
    }
  ]
}
```

`sw.js` must never be cached by an intermediary — that header is the whole update mechanism. The
rewrite is a fallback only; real files (`/game.js`, `/styles.css`, `/icons/…`) are served from the
filesystem first.

```bash
cd dutchkem-lagos-run
export API_BASE_URL=https://dutchkem-lagos-run-api.onrender.com   # the Render host
node build.js --prod                                              # writes dist/ incl. vercel.json
cd dist && npx vercel --prod                                      # static deploy, no build step
```

Project → Settings → Root Directory must stay empty for this flow; the deployment is the contents of
`dist/`. A git-connected project instead needs `API_BASE_URL` and the other public variables set in
the Vercel dashboard, because `dist/` is gitignored.

### 8.2 Netlify

`netlify.toml`:

```toml
[build]
  command = "npm run build"
  publish = "dist"

[[headers]]
  for = "/sw.js"
  [headers.values]
    Cache-Control = "no-cache, no-store, must-revalidate"
    Service-Worker-Allowed = "/"

[[headers]]
  for = "/config.js"
  [headers.values]
    Cache-Control = "no-cache"

[[headers]]
  for = "/icons/*"
  [headers.values]
    Cache-Control = "public, max-age=31536000, immutable"

[[headers]]
  for = "/*"
  [headers.values]
    Strict-Transport-Security = "max-age=31536000; includeSubDomains; preload"
    X-Content-Type-Options = "nosniff"
    Referrer-Policy = "strict-origin-when-cross-origin"
    Permissions-Policy = "camera=(), microphone=(), geolocation=()"

[[redirects]]
  from = "/*"
  to = "/index.html"
  status = 200
```

Netlify rewrites only when no file matches, so the shell fallback cannot shadow real assets.

`firebase.json`:


```bash
firebase deploy --only hosting
```

### 8.4 Custom domain, TLS 1.3, HSTS

1. Add `lagosrun.dutchkem.com` to the host and create the DNS record it gives you.
2. Let the host issue the certificate; confirm TLS 1.3 in the browser (Security → Connection) and that
   HTTP/2 or HTTP/3 is negotiated.
3. Force HTTPS and enable HSTS with `includeSubDomains` **only after** every subdomain is HTTPS —
   otherwise you brick `api.` for a certificate cycle. Submit to the preload list once stable.
4. Keep the API on its own hostname (`api.lagosrun.dutchkem.com`); the client's CSP and
   `ALLOWED_ORIGINS` both assume that split.

## 9. Auto-Update Flow

```
 build.js                     host                     browser
 ────────                     ────                     ───────
 rewrite CACHE_VERSION  →  deploy dist/  →  sw.js fetched (no-cache)
   dutchkem-v1.0.0-a1b2c3                        │
                                                 ├─ byte-diff? → install
                                                 │     precache new shell
                                                 │     skipWaiting()
                                                 │
                                                 ├─ activate → delete old
                                                 │     caches, claim clients
                                                 │     postMessage SW_UPDATED
                                                 │
                                                 └─ client shows "Update ready"
                                                       → reload on tap
```

Steps the player experiences: a new `sw.js` is always fetched with `no-cache`; because the
`CACHE_VERSION` line changed, the browser sees a byte-different worker, installs it, precaches the new
shell, activates, deletes the previous `dutchkem-lagosrun-*` cache and claims open clients. The client
listens for `SW_UPDATED` and offers a reload. If a player closes the tab mid-install, the next launch
finishes it — the new cache is already complete.

**Force update.** `backend/data/version.json` is served by `GET /api/version`:

```json
{ "version": "1.0.1", "minSupported": "1.0.1", "forceUpdate": true, "releaseNotes": "…" }
```

The client compares its `APP_VERSION` against `minSupported`. Below it, the game blocks play behind a
"Update required" screen and reloads the worker; `forceUpdate: true` additionally suppresses "Play
anyway". To force an update:

1. Bump `APP_VERSION` in the client `.env`, rebuild, redeploy the client.
2. Publish the matching `version.json` (same `version`) with the new `minSupported` and
   `forceUpdate: true`.
3. Players on the old build are blocked until they load the new shell.

Order matters: **deploy the new client before raising `minSupported`**, otherwise players are told to
update to a build that is not live yet.

`version.json` is read on every request (no cache), so a change takes effect on the next launch without
a backend redeploy.

## 10. Remote Config & Feature Flags

Two HMAC-signed JSON files, both under `backend/data/`, both editable without a code deploy:

| File | Endpoint | Contents |
|------|----------|----------|
| `remote-config.json` | `GET /api/config/remote` | brand, `features.*`, `ads.*`, `economy.*`, `events[]` |
| `rules.json` | `GET /api/config/rules` | `antiCheat.*`, `rewardedAdCaps.perDay`, `skuGrants` |

Both are returned as `{ data, signature }` where the signature is an HMAC with
`SCORE_SIGNING_SECRET`. A captive portal or CDN cannot rewrite economy values without failing
verification, and the client refuses an unsigned or mismatched payload.

Flags available today (`remote-config.json → features`): `crews`, `battlePass`, `fleetInvestment`,
`ghostRacing`. Ads knobs: `interstitialEveryRuns`, `rewardedPerDay`, `adFreeAfterPurchase`,
`ssvEnabled`, `rewardAmountCoins`. Economy: `fareMultiplier`, `offlineFleetCapHours`,
`dailyRemittanceTarget`. `events` is an array for time-boxed seasons; ship an empty array to disable
all events.

Operational playbook:

- **Kill switch for ads:** set `ads.ssvEnabled: false` (clients stop requesting verification; rewards
  pause) rather than removing the route.
- **Disable a feature:** set `features.<name>: false`. The client hides entry points on next config
  refresh; do not delete the code.
- **One change at a time**, one file per change, and keep the previous version alongside it so rollback
  is a copy, not a rewrite. `Cache-Control: public, max-age=60` means a change propagates within a
  minute.
- **Restart-free**: the routes read the file per request. No deploy, no process bounce.
- Changes to `skuGrants` and `antiCheat` are security-relevant — treat the file as reviewed
  configuration, not a scratchpad, and log every edit in the security log.

## 11. Monitoring & Alerts

| Signal | Tool | What it watches | Alert threshold |
|--------|------|-----------------|-----------------|
| Uptime | Better Uptime (or equivalent) | `GET https://api.lagosrun.dutchkem.com/health` every 60 s, from ≥2 regions | Down for **2 minutes** → page on-call |
| Errors | Sentry (backend + `SENTRY_DSN` in client) | Unhandled exceptions, 5xx, worker crashes | **5xx > 1%** of requests over **5 minutes** → page |
| Product analytics | Firebase Analytics | Session starts, run completion, crash-free users, funnel drop-off | Crash-free < 99% → ticket; run-abandon spike > 20% w/w → investigate |
| Fraud | `ADMIN_WEBHOOK_URL` (Slack/Discord) | Signature failures, ceiling breaches, underpaid webhooks, ban triggers | **3+ events in 1 hour** → page security |
| Ad integrity | SSV logs | Callbacks rejected / nonce expired vs granted | **Mismatch ≥ 5%** of SSV callbacks over an hour → check key rotation and AdMob config |
| Hosting | Vercel/Render dashboard | Build failures, cold-start latency, bandwidth | Build fail → block release; p95 latency > 800 ms → scale |
| Payments | Kora dashboard | Failed charges, webhook delivery failures, settlement | Any webhook delivery failure → replay and investigate |

Alerting rules of thumb: page only on player-visible or money-visible symptoms; everything else is a
ticket. Every alert links to this document and the runbook in §13. Test the pager path once a quarter
by stopping the API for two minutes in staging.

Log lines that must exist (grep-able, no secrets):
`[scores] signature mismatch`, `[scores] … above ceiling`, `[purchases] webhook rejected`,
`[purchases] underpaid`, `[ads] SSV callback rejected`, `[ads] granted … coins`,
`[user] deleted all data for …`.

## 13. Rollback

**Client.** Each build writes a unique `CACHE_VERSION`, so rolling back means redeploying the previous
`dist/`:

```bash
git checkout <previous-release-tag>
npm ci && npm run icons && node build.js --prod
npx vercel --prod          # or: netlify deploy --prod --dir=dist
```

Players pick up the rollback on their next visit; the old worker's caches are deleted on activate.
Never delete `dist/` from the host without deploying a replacement shell — that leaves installed
players with a shell that cannot update. If a bad worker was published, also bump `APP_VERSION` so the
cache name changes and no stale asset can be reused.

**Backend.** Roll back to the previous deployment in the host dashboard (Vercel → Deployments →
Promote; Render → Rollback; Cloud Run → route traffic to the previous revision). Keep the previous
release's environment variables intact; a rollback with rotated secrets will fail closed, which is the
correct behaviour — restore the old secret version only if the rotation itself was not the reason for
the rollback.

**Database.** Take a snapshot before any release that touches `db.js` or the schema. Restore procedure:
stop the API, replace the store from the snapshot, start the API, verify `/health` and one wallet
read. Accept that purchases verified after the snapshot must be reconciled against the Kora dashboard —
never silently re-grant them.

**Force-update escape hatch.** If a broken client cannot be replaced quickly, publish
`version.json` with `forceUpdate: true` and a `minSupported` above the bad build to block it, then
deploy the fix.

## 14. Scaling Notes

- **Swap the file store for Postgres before 10k DAU.** `services/db.js` persists one JSON file per
  process: it does not survive serverless invocations, does not coordinate across instances, and
  rewrites the whole document per mutation. Supabase/Postgres with indexed `uid` lookups is the first
  scaling step, not an optimisation. Keep the same service interface so routes do not change.
- **Put Cloudflare in front** of both hostnames at the first sign of abuse: WAF rules for the
  `/api/purchases/*` and `/api/ads/*` paths, bot-fight on `/api/session`, rate limits at the edge that
  mirror the in-app limiters, and cached static assets. Keep the Kora webhook path on a cache bypass
  and preserve the raw body.
- **Turn on AdMob SSV before spending on ads.** Without server-side verification, rewarded revenue is
  farmable and the account is at risk of an AdMob policy strike. `ads.ssvEnabled` must be `true` in
  production before any paid install campaign.
- **CDN for static assets.** `dist/` is immutable except `sw.js`, `config.js` and `manifest.json`;
  cache icons and fonts for a year with hashed names, and never cache `sw.js`.
- **Read scaling.** Leaderboard reads dominate. Cache `/api/scores/leaderboard` at the edge for
  30–60 s; the route already sends `Cache-Control: public, max-age=30`.
- **Write scaling.** Score and reward writes are small and idempotent. Batch reward counters, and keep
  the wallet update in one transaction once Postgres lands.
- **Watch the nonce map.** SSV nonces are in-memory per process; with several instances a callback can
  land on the wrong one. Move nonces to Redis/Postgres when you scale past one instance.
- **Capacity target.** One small instance handles launch traffic comfortably; scale on p95 latency
  above 800 ms or sustained CPU above 70%, not on request count.

## 15. Native Build Notes

The PWA is the primary product; native shells exist for store distribution and store billing. **Kora
Pay is web/PWA only** — do not embed a card form in a native shell.

### Android

- Wrap the client with Capacitor or a Trusted Web Activity, package id `com.dutchkem.lagosrun`.
- Replace the web checkout with **Google Play Billing**: query products (`kobo100`, `kobo500`,
  `kobo1200`, `kobo2500`, `kobo6500`), launch the purchase flow, and send the purchase **token** to
  `POST /api/purchases/verify` with `{ "platform": "google", "receipt": { … } }`.
- The backend validates with the Play Developer API using `GOOGLE_PLAY_SERVICE_ACCOUNT_JSON` and
  `GOOGLE_PLAY_PACKAGE_NAME`; the SKU is mapped through `SKU_MAP`, an already-redeemed `txnId` is
  rejected with `409`, and kobo is credited only on success.
- Consume/acknowledge the purchase after the API confirms, so Play does not auto-refund it.
- If Play Billing is unavailable in a region, keep the Kora flow in a Custom Tab rather than a native
  form — Kora's hosted checkout is PCI-scoped, ours is not.

### iOS

- Wrap the client with Capacitor, bundle id `com.dutchkem.lagosrun`.
- Use **StoreKit 2**. Send the App Store receipt (or the JWS transaction) to
  `POST /api/purchases/verify` with `{ "platform": "apple", "receipt": "…" }`.
- The backend calls Apple's `verifyReceipt` with `APPLE_SHARED_SECRET` and automatically retries the
  sandbox endpoint (`21007`) so TestFlight receipts validate.
- Finish the StoreKit transaction only after the API confirms the grant; otherwise the player can be
  charged without receiving kobo.
- App Review note: digital currency must be sold through IAP on iOS. Do not surface the Kora button in
  the iOS shell.

### Shared rules for both shells

- The `SENTRY_DSN` and ad unit ids are public; the Kora secret, Play service account and Apple shared
  secret never enter the app bundle.
- Keep the same anonymous-uid session flow so a player's wallet is identical on web and native.
- The `version.json` force-update gate applies to shells too: publish `minSupported` per platform and
  read it at launch.
- Store builds still require the PWA's privacy policy URL and data-deletion statement, which
  `GET /api/user/export` and `DELETE /api/user/me` already satisfy.
